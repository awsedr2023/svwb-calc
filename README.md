# SVWB ドロー確率計算

Shadowverse: Worlds Beyondで、指定ターンに対象カード1枚を手札に確保し、そのカードの使用PPも残せる確率を計算する非公式ツールです。

TypeScript + Preact + Vite。サーバー、API、カードデータベースは不要です。計算はWeb Worker内で行い、GitHub Pagesに静的ページとして配置できます。外部フォントや解析サービスへの通信もありません。

## 初版の仕様

- 40枚デッキ。対象は1グループ・採用1〜40枚・コスト0〜6。目標は1〜5ターン。
- 固定コストの即時ドロー／サーチソースを合計5グループまで登録。各1〜40枚、コスト0〜6、通常ドロー1〜5枚・ランダムサーチ1〜40枚。同じ効果・コストのカードをまとめて入力できる。
- サーチ対象は狙うカード、各ソース、その他の候補グループ（最大3組）から選択。複数サーチで同じグループを選ぶと、候補の残枚数を共有する。対象・有効なソース・その他の候補の合計は40枚以内。
- 各ソースの「有効」チェックで一時的に計算対象から外せる。無効時はその枚数を「その他」に含め、初手交換でも残さない。設定値とチェック状態は保存され、再度有効にすれば元の条件に戻る。
- 対象カードとドローソースは別カードとして登録。残りのカードは効果を持たないカードとして扱う。
- 初手4枚、通常ドローは先攻・後攻とも各ターン1枚。
- 初手に対象があれば保持。なければ「各ソースを指定枚数（0〜3枚）まで保持」と「すべて交換」の2方針を比較。旧保存データの「残す」および4枚指定は3枚まで、「残さない」は0枚へ移行。
- 既定の「成功確率を最大化」では、サーチの当たり確率・使用順・何も使わず次ターンへ進む選択・後攻のエクストラPP1回の使用／温存を比較する。未来の引き順を知らず、その時点の情報から期待成功率が最大の行動を選ぶ。キープ枚数自体は最適化しない。
- 画面上の行動方針は成功確率最大化に統一。旧保存データも読み込み時に最大化へ変更する。従来の取得枚数優先方針は検証用に内部実装のみ残し、上限時にも自動で切り替えない。
- 先攻・後攻、初手交換2方針を同時計算。グラフ/表の切り替え、条件と結果を1件固定した差分比較。
- 現在の入力はブラウザに自動保存。固定した比較条件はタブを閉じると消える。
- **手札上限は考慮しない。** 盤面、通常の展開に使うPP、相手の行動、進化、PPブースト、選んで加えるサーチ、条件付き効果、コスト変動も範囲外。

## モンテカルロによる検証

「詳細設定」は通常閉じており、計算量上限を10万〜200万状態（10万刻み、標準40万）に変更できます。設定は保存されます。上限を増やすほどメモリ消費が増えます。時間制限（1シナリオ約12秒・全体約25秒）は変更しません。

このシミュレーションは従来の取得枚数優先方針を検証するものです。成功確率最大化は `tests/optimal.test.ts` の独立した現物カード全探索192条件、解析的なサーチ成功率、従来方針との大小関係などで検証します。

`npm run verify:mc` で36条件を各10万回（合計360万回）シミュレーションし、厳密計算と比較できます。試行数の変更は `npm run verify:mc -- 200000`。固定シードにより再現可能です。

検証用実装は本体の初手交換・行動選択・抽選処理を使わず、40枚のカード配列からランダムに取得します。通常ドロー、枚／種類サーチの連鎖、先後、初手保持／全交換、エクストラPPの2方針、6PP対象、無効ソース、候補枯渇、山札切れを含みます。合否の許容差は実行前にHoeffding不等式とunion boundで定め、独立試行を仮定した全比較の誤警報確率を0.1%以下に設定しています。これは統計的な照合であり、正しさの証明やゲーム仕様自体の検証ではありません。

## サーチの入力例

カードカテゴリは有効・無効を切り替えられます。無効時はサーチ・キープ・採用枚数合計の対象外となり、40枚デッキの残りは「その他」として扱います。設定値は保持され、再び有効にすると元に戻ります。

「カードカテゴリ」もグループごとに初手保持0〜3枚を指定できます。初期値・旧保存データは0枚です。サーチを無効にしても保持設定は有効で、「指定枚数を残す」と「すべて交換」の比較に反映します。

1. ソースの「効果」を「ランダムサーチ」に変更し、コスト・サーチ枚数n・採用枚数を入力する。
2. 「サーチ対象」で狙うカードや該当するソースを選ぶ。
3. それ以外に候補が7枚あるなら「カードカテゴリを追加」で7枚と入力し、そのグループもサーチ対象にチェックする。

指定枚数は初期デッキ内の枚数です。残り枚数の入力は不要で、通常ドローや初手交換、別のサーチで減った枚数は自動追跡します。「サーチ単位」で「枚／種類」を選択できます。「枚」は同名カードを複数枚取得でき、「種類」は異なるカード名を各1枚取得します。残り枚数に比例して1枚ずつ抽選し、「種類」ではそのサーチ中に選んだ種類を候補から外します。候補が足りなければ残りだけ加え、候補0枚のサーチは使いません。旧設定は「枚」として扱います。

「種類」では対象・各ソース・その他の各登録グループをそれぞれ1種類と数えます。同じ効果でも別名のカードは分けて登録してください。

「その他」グループ同士は重複させずに登録してください。例えばサーチAだけの候補、Bだけの候補、A・B共通の候補に分け、それぞれのサーチで該当グループを選ぶと重なりを表現できます。無効なソースはサーチ対象からも外れます。

各ターンを別々の目標として計算します。例：3ターン目の点は3ターン目に対象用PPを残し、5ターン目の点は5ターン目に残す方針です。同一のプレイ履歴の累積確率ではありません。方針によっては確率の列が単調増加するとは限りません。

## スマホと計算量

画面の処理と計算を分離しています。入力変更で古いWorkerを終了し、300msの入力待ち後に計算。目標ターンの切り替えは計算済みの結果を表示するだけです。中止操作、計算量の上限、25秒のタイムアウトを設けています。上限時に不完全な確率やシミュレーション値を代わりに表示することはありません。

成功確率最大化を開発環境のNode.js 22で測定（2026-09-06、先攻/後攻 × 初手交換2方針 × 全5ターンの合計、キープがすべて0なら同一方針を再利用）：

| 条件                                  |                計算時間の目安 |
| ------------------------------------- | ----------------------------: |
| ドローソースなし                      |                       1ms未満 |
| ドローソース1種類・既定値             |                           1ms |
| ドローソース3種類                     |                          69ms |
| ドローソース5種類・通常のコスト       | 状態数の上限で停止（約0.9秒） |
| ドローソース5種類・低コスト大量ドロー |            状態数の上限で停止 |

ケースの全入力は `scripts/bench.ts` を参照してください。これはスマホ実機のベンチマークではありません。ブラウザテストのモバイル設定も、画面幅とタッチ操作の模擬です。端末のCPU・メモリ・熱状態により待ち時間は変わります。

最大化では、2枚サーチ1種類＋その他候補7枚の例で約18msでした。通常ドロー1種類＋サーチ2種類＋一部が重なるその他候補3グループの例は、約2.6秒で状態数の上限に達しました。従来方針で完了していた5種類の例も最大化では上限に達します。サーチ対象の重なりとグループ数で計算量が増え、入力可能な条件でも上限内に完了するとは限りません。

## GitHub Pagesへの公開

1. この内容をGitHubリポジトリの `main` ブランチへ配置する。
2. リポジトリの **Settings → Pages → Build and deployment → Source** を **GitHub Actions** にする。
3. `main` へのpush、またはActions画面で `Build and deploy to GitHub Pages` を実行する。

同梱の `.github/workflows/pages.yml` がテスト・ビルド後に `dist/` を公開します。PRでは検証のみを実行します。`base: './'` により `https://ユーザー名.github.io/リポジトリ名/` にも対応し、WorkerのURLもViteが処理します。HTMLのダブルクリック（`file://`）ではなくHTTPサーバーで確認してください。

この作業ではGitHubリポジトリ作成・push・実際の公開は行っていません。
