# 計算と画面の設計

## 成功確率最大化（既定）

`extra: 'optimal'` は、ドロー・サーチ・エクストラPPを一体で最適化する方針。行動を選ぶ状態では、各使用可能ソース × 追加PP使用／不使用と、何も使わず次ターンへ進む行動の期待成功率の最大値を取る。抽選中は候補残枚数に比例した加重平均を取る。最大値は抽選結果を見る前に取るため、未観測の引き順を知った全知的な最適化ではない。

対象の使用PPを残せない行動は除外する。手札のソースは使うごとに減り、ドローで山札が減るため0PPでも循環しない。メモ化キーは既存の状態表現を共用できる。状態数・時間上限は従来どおりで、上限時に不完全な最大値を返したり従来方針へ自動変更したりしない。

最適化範囲はマリガン後の行動のみ。キープ枚数は指定どおりで、対象確保後に追加ドローを止める、手札上限なし、盤面・相手の行動なし等のモデル内で最大化する。画面からの方針選択は削除し、旧保存データの `greedy` / `reserve` も `loadConfig` で `optimal` に変更する。検証用の内部APIでは従来方針も維持する。以下の取得枚数ベースの行動選択・追加PP判断の記述は従来方針に適用する。

検証は `tests/optimal.test.ts`：本体のメモ化・探索補助を使わない現物カードの期待値最大化192条件、確実／不確実なサーチと通常ドローの比較、山札切れ回避、40枚デッキで従来2方針以上の成功率を確認する。従来モンテカルロは最適化方針の検証ではない。

## 成功条件

### 枝刈りと状態統合

`Limits.pruning` は診断用で、`false` なら4対策を無効にできる。通常はすべて有効。追加PPなしで払えるソースでは、追加PPを先に使う分岐を省く（効果解決中にPPを使わず、必要時まで使用を遅らせられるため）。最終ターンは未使用追加PPを通常PPへ合算して同じメモ化キーへ正規化する。

サーチありの場合のみ、対象を直接引ける見込みが高い行動から探索する。この順位付けは近似だが、順位だけで枝を切らず、得られる確率は厳密な期待値。確率1の行動が得られた時点で他の行動を調べない。

抽選ノードでは「集計済み成功分＋未探索候補の確率質量」を上限とする。競合する行動の確定値より `1e-12` 以上小さい場合のみ打ち切る。この上限値は呼出元の最大値を改善できず、メモには保存しない。閾値は行動直後の抽選ノードにのみ渡し、その子の計算は正確な値を返す。メモに保存される値は常に正確な期待値（浮動小数点の丸めあり）。

目標ターンTに対象カード1枚以上が手札にあり、その使用コストCを払えること。対象はそれ以前に引いても保持し、Tに使用する。PPを使う行動は登録したドローソースと対象だけ。

手札上限はユーザー指定でモデルから除外。山札切れは失敗。対象を引いた効果の残りドローも解決するため、途中で対象が見えても同じ効果で山札切れになる場合は成功にしない。対象確保後は追加ドローを止め、目標ターンまでの通常ドローだけ継続するものとして判定する。

ドローソースの有効・無効は設定を保持したまま切り替える。無効なソースは計算前に除外し、その採用枚数は40枚デッキの「その他」に含める。初手保持も対象外となる。保存・固定比較には無効の設定も含め、旧保存データで有効フラグが未指定の場合は有効として扱う。

## 行動方針

### 初手交換

初手に対象があれば成功条件のPP到達可能性だけ確認する。なければ次の2方針を別計算する。

1. 各ドローソースを、指定した保持上限（0〜3枚）と実際の初手枚数の小さい方だけ残し、その他を交換。
2. 4枚すべて交換。

交換後に対象を得た場合は保持。有効なドローソースの保持上限がすべて0なら2方針は同一なので結果を再利用する。旧保存データの真偽値はtrueを4、falseを0に移行し、保持方針を維持する。保持上限は初手交換にだけ使い、交換後の手札や通常ドローには適用しない。

### ドローソース

手札にあるソースの組み合わせを全探索し、予算PP内で効果の合計ドロー枚数が最大となるものを選ぶ。比率だけで単体カードを選ぶ方式ではない。

- 同じドロー枚数なら合計コストが低い組み合わせ。
- さらに同点なら低コスト・多ドロー・登録順のソースを多く含む組み合わせ。
- 選んだ組み合わせ内では低コスト・多ドロー・登録順で1枚使う。
- 効果で引いたカードを手札に加え、組み合わせを再計算する。
- 目標ターンの予算は `残りPP - 対象コスト`。対象がまだ見えていなくても確保する。

これは現在の手札から多く引く規則であり、将来の引きや成功率全体を最大化する探索ではない。山札切れが起きる特殊な入力でも、この規則そのものは変更しない。

### エクストラPP

通常PPと未使用フラグを別々に保持する。使った後の追加PPは次ターンに持ち越さず、使用済み状態だけ持ち越す。

`greedy`（従来方針）：通常予算と+1した予算でそれぞれ組み合わせを求め、合計ドロー枚数が増えるなら使用。

`reserve`：目標ターンより前は使用しない。目標ターンで必要な場合に使用。

どちらの場合も `C = T + 1` なら対象用に温存し、早いターンのドローには使用しない。`C > T + 1` は後攻でも0%。先攻は `C > T` なら0%。対象を手札に持つ場合はソースを使わず、必要ならエクストラPPを対象に回す。

## 厳密計算

### ランダムn枚／n種類サーチ

`search.unit` は `cards`（枚、未指定時の既定）または `types`（種類）。種類モードでは各登録グループが1つのカード名を表すため、別名カードをまとめて登録しない。取得上限は残っている候補種類数。抽選は候補の残枚数に比例し、選ばれた種類をその効果の残りの抽選から除外する。解決中の選択済み種類をビットマスクで追跡して状態キーに含め、効果終了時にリセットする。以下の枚数ベースの説明は枚モードに適用する。

ソースの `kind: 'search'` と `search: { target, sources, others }` でサーチ対象を指定する。通常ドローは `kind: 'draw'` または未指定。カードカテゴリは `searchOthers` に重複しないグループごとの採用枚数を保存し、複数のサーチが同じグループを参照できる。各グループは通常ドロー・初手交換でも別のカード種類として追跡する。

サーチ開始時に候補残数Kを計算し、取得枚数を `min(n, K)` にする。解決中は選択可能な種類の残数/Kで分岐し、選ばれた種類の山札枚数を1減らして手札へ加える。各カードの現物は取り出すため、同じ現物を二重取得しない。同じ種類の別コピーは取得できる。候補0枚のサーチは方針上使わず、山札切れの通常ドローとは区別する。

ソースを検索対象に含めた場合、取得したカードも同ターンの行動に使用できる。サーチ自身の別コピーも対象にできる。無効なソースは計算時に除外し、参照番号を詰め直す。削除時もサーチ参照を更新して、別のソースへ意図せず参照が移らないようにする。

ドローとサーチを選ぶ際は現在の手札の取得枚数を基準にする。サーチの評価枚数は現在の候補残数で上限をかける。効果1回ごとに候補残数を再評価し、候補0枚のサーチにPPやエクストラPPを使わない。複数の検索範囲が重なる場合の組み合わせ評価は、各効果単体の上限を足した値。将来の抽選や候補の取り合いを含む最適化ではない。

サーチが含まれる場合、状態キーには解決中の効果の種類と検索範囲も必要となる。その他候補グループの残枚数も含めた文字列キーを使い、通常ドローのみのケースでは従来の数値キーを維持する。通常ドローとサーチで同じ状態キーが衝突しない。計算量の上限・中止・タイムアウトはサーチでも同じ。

### 状態の集計

初手と交換は多変量超幾何分布で枚数構成ごとに集計する。プレイ中は次の状態をメモ化する。

`ターン / 残りPP / エクストラPP未使用 / 解決中のドロー残数 / 山札の種類別枚数 / 手札のソース別枚数`

山札からの1枚ドローを、種類ごとの `残枚数 / 山札枚数` で分岐。同じ状態に到達した経路は再利用する。対象入手後は必要PP・残り通常ドロー・効果の解決を確認して分岐を終える。成功前の対象カード枚数は一定なのでキーに含める必要がない。

各ソースの採用枚数をcとすると、山札・手札・使用済みに分かれる枚数構成は `(c+1)(c+2)/2` 通り。種類ごとにこの基数を計算し、山札d枚・手札h枚を `d(2c+3-d)/2+h` で符号化する。これとその他の山札残枚数、ターン、PPなどを混合基数の数値キーにして、文字列キーのメモリ確保を減らしている。手札上限を扱わないため、その他の手札枚数はキーから除外できる。使用方針のキャッシュも、各ソースの手札枚数を基数c+1で符号化する。

範囲内の各シナリオで全分岐を集計する。浮動小数点の丸めはあるが、モンテカルロによる標本誤差はない。結果を%表示するときだけ小数2桁に丸める。

入力の採用枚数は対象・ソースとも1〜40枚。対象・有効なソース・カードカテゴリの合計が40枚を超える場合は計算を開始しない。無効なソース設定は計算に入らないため合計にも加えない。ソース5グループ、カードカテゴリ3グループ、通常ドロー5枚・サーチ40枚、5ターン、最大6PPの制限がある。数値キーを使う通常ドローのみのケースでは、有効なソース枚数の合計は最大39枚。この範囲で数値キーはJavaScriptの安全な整数範囲内。上限を変更する際は基数・状態容量・テストも同時に確認すること。

## 計算負荷と結果の整合性

- 1シナリオにつき40万メモ化状態、12秒を上限とする。
- 画面側はWorker全体を25秒で停止。ブラウザのタイマー遅延で厳密な実時間上限にはならない。
- 処理はWorkerに限定し、UIスレッドで計算にフォールバックしない。
- 条件変更時に旧Workerを破棄。結果には条件キーを対応させ、古い値を新条件の結果として表示しない。
- 不正な入力中は結果と固定操作を無効化。入力欄を離れると最後の有効値に戻す。
- 直近3条件をキャッシュ。目標ターン選択だけなら全ターンの計算結果を使う。
- 上限に達した場合、途中の値を完成値として出さず、条件を減らす案内を表示。
- 固定比較は入力と結果を一緒に複製。差は同じターン・先後・初手交換方針で求める。

## フロントエンド

TypeScript + Preact + Vite。チャートはSVGで描画し、大きなチャートライブラリは追加しない。入力・計算状態と表示をPreactで管理する。結果の表とグラフは同じ数値を使用。

PCでは左右2列、スマホでは縦配置。スマホは下端に確率の要約と結果への移動リンクを表示。条件を変えるたびにページ下部へスクロールしなくても結果の概要を確認できる。

実行時の通信は静的アセットの取得のみ。ブラウザの保存が拒否された場合も計算は継続。カード画像・カード名データベースは持たない。

## 検証

- ドローソースなしの確率を閉じた数式と照合。
- 初手分布の総確率、交換後の山札、対象枚数を確認。
- エクストラPPで初めて払えるコスト、使用済みフラグ、温存、目標PP確保。
- 0コストの連鎖、9枚超の手札、効果解決中の山札切れ。
- 6枚の山札の720通りの物理順序を独立シミュレーターで全列挙し、先後・コスト・ターン・PP方針を変えた60条件で厳密計算と照合。
- PlaywrightでPC・スマホ幅、比較・入力保存・再計算・エラー回復、GitHub Pages相当のサブパスからWorkerをロードする動作を確認。

モバイル画面のエミュレーションは実機のCPU速度・メモリ制約を再現しない。スマホ実機の追加測定は公開前の推奨確認事項。
